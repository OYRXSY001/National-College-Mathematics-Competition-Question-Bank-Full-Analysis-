# 数学竞赛题库系统 · 对外上线运营优化方案（修订版）

> 制定日期：2026-08-27
> 口径：对外上线运营 + 全项目覆盖（Web + 小程序 + 导入流程 + 部署运维）
> **重要决策 1（2026-08-27）：域名 ICP 备案列为暂缓项**，Web 端不做公网发布，相关技术选型规避备案依赖。
> **重要决策 2（2026-08-27 当日二修）：整体目标模型确定为「分发自用」**——不运营站点，把项目打包发给他人、对方在本机自行部署使用。据此第二节起的运营类项全部降级，新增 M-D 分发工程模块，详见文末「口径二次修订」。

## 一、现状分析

### 当前概况
- 架构：Django 5.2 Web 端 + 微信小程序端，收录第 1–17 届共 39 卷 / 254 题，KaTeX 公式渲染（Web 页面 auto-render，小程序本地 katex-bundle）。
- 数据流：Excel 工作簿 → `import_question_bank`（dry-run / 正式）→ 手动置 published；小程序侧另有独立一套 SQL chunks 导入云数据库，同时 416KB 的 `questions.js` 全量硬编码打进主包。
- 基建：SQLite 单文件库；`deploy/` 已备好 Caddy + systemd gunicorn + 每日备份脚本；测试实际 90 个（README 曾宣称 104，数字失真已修正）；无 CI、无监控、无缓存层、无错误上报。

### 核心问题拆解（根因分析）

| # | 表象问题 | 根因 |
|---|---|---|
| P1 | 双端数据易漂移 | 缺统一数据出口。小程序走"内置数据换离线可用"的架构捷径，没有配套同步流程，DB 与 JS 快照靠人工双写，必然发散 |
| P2 | 小程序包体持续膨胀 | 增长型数据用了静态打包策略。每届新增 15~25KB，questions.js 已 416KB，叠加 KaTeX bundle 与字体，距主包上限余量被逐年吃掉 |
| P3 | 内容上新全靠人肉 | 流程存在于 README 文档而非脚本：导入→复核→浏览器检查→手写 Python 翻状态，共 6 步无完成判据、无自动回滚 |
| P4 | 工作区/Git 卫生差 | AI 高频迭代产物无入库前清理环节：根目录堆积误生成物；gitignore 规则不全，存在误提交风险 |
| P5 | 账号体系单薄 | 注册仅用户名、无邮箱、无找回密码；小程序另有独立登录，两端账号不互通 |
| P6 | 内容分发的合规边界未想清 | 小程序教育类目有资质门槛；无备案域名导致 Web 端无法正轨公网化——后者已决策暂缓，前者仍需在小程序提审前处理 |

## 二、优化总体思路与原则

**总体思路**：先止血（卫生/安全/备份）→ 再通脉（统一数据源与同步管线）→ 后增益（体验/运营指标）。**约束**：本期所有内容分发路径绕开备案依赖——小程序走云开发（微信云开发不需要配置已备案的 request 合法域名），Web 端停留在局域网/IP 试运行。

**五条原则**：
1. **规模匹配**：254 题、初创期流量的站点，拒绝过度设计——不上 PostgreSQL 分库、Elasticsearch、Redis、K8s。
2. **单一事实源**：Django DB 为唯一数据源，Web 与小程序均为派生视图。
3. **一切流程脚本化**：能一条命令完成的绝不写在文档里让人照抄。
4. **发版与数据解耦**：题库内容更新不得依赖微信发版审核。
5. **备案挂起下的替代通道**：凡涉及"对外触达"的能力优先落在小程序+云开发上；Web 端能力建设照做，但不依赖公网域名兑现。

## 三、优化目标（量化）

**本期非目标（明确排除）**：域名注册、ICP 备案、Web 端公网发布与 SEO 收录。恢复条件：确认要做公开运营时，从提交备案到可公开约需 3–4 周，作为独立小项目再启动（预写清单见 M8「备案后启动清单」）。

**短期（≤2 周）**
- `git status` 干净：ignore 规则覆盖全部生成物，工作区零散文件归档完毕；README 数字与实测一致。✅ 已于 2026-08-27 完成
- 安全基线一次落地：DEBUG=0 运行、admin 路径隐蔽 + 认证接口限速、SQLite 开 WAL。
- 找回密码链路可用（邮箱）；Sentry 免费版接入，错误知晓时效 < 24h。
- 备份增加异地副本，并完成 1 次**恢复演练**（不是只备份）。

**中期（1–2 月）**
- 小程序主包腾挪出 ≥ 400KB 余量（questions.js 移出主包），内容可热更不发版。
- 新一届题库导入端到端 ≤ 0.5 人天（含小程序数据同步 ≤ 1 人天），管线脚本驱动并有失败中断点。
- GitHub Actions 全绿门禁生效，测试总数回升至 ≥ 100。
- 小程序提交审核并过审（若走提审）：类目资质自查通过。

**长期（3–6 月）**
- 以第 18 届上线为验收战役：从拿到 PDF 到双端可见 ≤ 1 人日。
- 运营指标基线建立：MAU、收藏率、错题本周活、搜索零结果率。
- SQLite → PostgreSQL 迁移触发条件明确并达成共识（见第五节 R5）。

### M2 Web 安全与账号体系　优先级 P0　工期 2–3 天　资源：1 名后端
- **具体动作**：补邮箱注册与密码找回、admin 加固、认证限速、备份异地化。
- **实施步骤**：
  1. `User` 增加 email 字段 + migration；复用 Django 内置 `PasswordResetView` 系列（仅需 2 个模板）；注册表单补 email。**方案对比**：django-allauth（功能全但依赖树大、模板定制成本高）vs 内置 auth 最小实现 —— 本规模推荐**后者**。
  2. admin：更换 `/admin/` 路径为随机段；登录/注册视图接 `django-ratelimit`（10 次/小时/IP）。
  3. `backup.sh` / 或本机等价脚本追加异地副本：对象存储 OSS/COS（约 1 元/月，rclone 直传），保留策略沿用 14 天。
  4. SMTP 用免费额度（QQ 企业邮即可），配 SPF/DKIM 防进垃圾箱。
- **建议资源**：对象存储约 12 元/年，其余免费。

### M3 运行环境落地与可观测性　优先级 P0　工期 2 天　资源：1 人

**部署形态对比（备案暂缓前提下）**：

| 选项 | 做法 | 适用 |
|---|---|---|
| **① 本机常驻（推荐）** | Windows 任务计划/waitress 自启（README 已有方案） | 当前阶段使用者少，零成本，今天就绪 |
| ② 海外/港区轻量 VPS | 免备案可直接绑域名对外 | 想尽快半公开时用；约 30 元/月；将来公开运营仍建议迁回国内备案 |
| ③ 国内 VPS + 域名 | 即原 deploy/ 方案 | **随 ICP 备案一起暂缓**，配置文件留着随时启用 |

- **实施步骤**：
  1. 先按①跑通 DEBUG=0（`.env` 生产开关全部生效，硬化不受形态影响）；deploy/ 三件套保留不动，未来切换零改造。
  2. 生产 SQLite 开 WAL：`PRAGMA journal_mode=WAL; busy_timeout=5000`。
  3. Sentry SaaS 免费版（5k errors/月）接入 Django——本机形态下 Sentry 是唯一可靠的错误感知渠道。
  4. `/healthz` 端点（DB 连通性）+ 本机计划任务每 5 分钟拨测异常即写日志/邮件。
- **建议资源**：本机形态零成本；Sentry 免费。

### M4 导入管线一键化　优先级 P1　工期 2 天　资源：1 人
- **具体动作**：把 README 里 6 步人工流程收敛为一条命令。
- **实施步骤**：
  1. 写 `pipeline.ps1`，参数只有届数：自动 `cp db.sqlite3 db.bak-{ts}` → dry-run → 交互确认 → 正式导入 → publish 翻状态 → `manage.py test` → `node browser_math_check.cjs`，任一步非零退出即中止并提示回滚命令。
  2. 抽象复用 `data/review/edition-*` 下重复的 build_import_workbooks*.py（A/B 类参数化合并）。
  3. KaTeX 校验（目前 subprocess 调 node）固化为管线前置步骤，报告留档。**由此生产环境无需安装 Node**。
- **建议资源**：复用现有脚本，纯改造。

### M5 小程序数据架构改造　优先级 P1　工期 3–5 天　资源：1 名前端（核心决策点）

**三方案对比**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 保内置+瘦身 | questions.js 拆子包懒加载 | 改动小、离线可用 | **内容更新仍需发版审核，运营上致命** |
| B 全量 API 化 | 数据全走 Django 接口 | 更新即时、账号打通 | **request 合法域名必须 ICP 备案——与暂缓决策冲突**，弱网首屏慢、失去离线 |
| **C 混合（推荐）** | 云开发数据库为主数据源，首发拉取+本地版本缓存 | 复用已建的 cloudfunctions 与云数据库；**全程免备案域名**；热更不发版；包体减 ≥400KB；国内延迟低 | 需维护一条 DB→云开发的同步管道 |

> 结论强化：在"备案暂缓"约束下，B 被直接排除，C 从"较优"变为"必然选择"。

- **C 落地步骤**：
  1. 定义 manifest 接口：`{build_id, question_count, content_hash}`；
  2. Django 新增管理命令 `sync_to_cloud`：DB 全量 → JSON → 经云开发 HTTP API 覆盖集合（或脚本化复用现有 SQL chunk 导入）；
  3. 小程序 `app.js` 启动比对 build_id，不同则拉增量入 storage；兜底保留一版精简内置数据（仅首页/搜索骨架所需 papers+知识点，约 56KB）；
  4. 删除 416KB 内置 `questions.js`；试卷 PDF 跳转官网下载的方式在 Web 未公网前暂不启用，可先不出入口；
  5. 灰度：manifest 控制放量比例，保留旧内置包一个版本周期作回退。
- **建议资源**：微信云开发基础套餐约 19.9 元/月。

## 八、补充建议

1. **明确"不做什么"同样是方案**：本期坚决不上 Docker 编排、Redis、微服务；所有组件等真实瓶颈出现再加。
2. **备案虽缓、避免返工**：本期代码不写死任何对"无域名"环境的假设（如绝对 URL），配置一律走 `.env`，这样备案落定当天即可零改动切公网。
3. **版权姿态宜保守**：题库免费的公共价值定位下，官方 PDF 来源清晰标注，能消除最大的法务敞口。
4. **高价值功能储备**（进需求池、不挤占本期）：基于已结构化的知识点树做"薄弱点诊断"和"按考点智能组卷"。
5. **推广物料隔离**：公众号文章、AI 封面等素材固定放 `docs/marketing/`，根目录永远只留代码与配置——配合 M1 固化后根治 AI 辅助开发的残留物问题。
6. **每届一发 tag**：`edition-17-published` + 同名数据库备份，形成时间机器。
7. **单人+AI 协作固定仪式**：每次会话结束过一遍 M1 清单，卫生问题从源头不再产生。

## 九、口径二次修订：从「对外运营」到「分发自用」（2026-08-27）

用户明确最终形态：**不需要 ICP/公网部署，只需把项目打包发给别人，收件人在自己电脑上自行部署使用**。原方案的运营前提被推翻，模块调整如下：

### 模块增降

| M5 小程序云开发热更改造 | **冻结**。当前内置数据模式反而是分发场景的最优解（离线可用、零后端）。仅当日后决定以自己的名义正式发布小程序并持续上新时再启动 | 消除"为了热更而热更" |
| M7 CI | 可选低成本保留；打包前本地跑 `manage.py test` 已足够 | 单人维护场景 |
